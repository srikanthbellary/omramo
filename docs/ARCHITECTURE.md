# Omramo — Architecture (v2, global English)

**Status:** plan for the v2 build. Nothing here is implemented yet.
**Reads with:** `docs/PRD.md` (what), `docs/DESIGN.md` (look), `docs/IMPLEMENTATION_PLAN.md` (order).

Markers: **Assumption** = my choice, reversible. **Unverified** = a platform fact I could not confirm from this Linux box (no Xcode, no Duo SDK, no Apple documentation fetched in this run). **Open question** = needs Srikanth or hardware.

---

## 1. Shape of the system

- One native iOS app, **SwiftUI**, no server, no account, no third-party dependency.
- One **pure-Swift package**, `OmramoCore`, holding everything that needs no UI framework: content model and parsing, validation, pane-layout maths, reading position, sample and entitlement rules, reading log and streak maths, and design tokens as plain numbers. It imports Foundation only and is testable with `swift test` on Linux or macOS.
- One **app target**, `Omramo`, holding SwiftUI views, fonts, StoreKit, persistence adapters and the Duo SDK adapter.
- Content is **data** (JSON plus images) in a top-level `Content/` folder, bundled into the app at M1 and loadable from a downloaded folder later through the same reader.

Dependency direction is one way: `Omramo` (app) → `OmramoCore`. The core never imports SwiftUI, UIKit or StoreKit.

## 2. Platform, language and minimum iOS

| Item | Choice | Why |
|---|---|---|
| UI | SwiftUI, with small UIKit bridges only where SwiftUI cannot do the job (variable-font axes) | Decided: native Swift |
| Language | Swift 6 toolchain. Core package in Swift 6 language mode; app target in Swift 5 mode with complete strict-concurrency checking | Same split the earlier scaffold used; keeps the core strict and the app pragmatic |
| State | Observation (`@Observable`), `@MainActor` stores | Needs iOS 17+ |
| **Minimum iOS** | **18.0 — assumption A7** | (1) `TextRenderer` and `Text.Layout` (iOS 18) give per-run glyph rectangles, which the reader needs for tap-word highlights, hit areas, the place marker and text on a path. (2) Observation and `SubscriptionStoreView`-era StoreKit need 17. (3) The app must run on an ordinary iPhone and the simulator today, before the Duo SDK is in hand. |
| Device family | iPhone (assumption). iPad is an open question (PRD Q1) | |
| Xcode | Version on the build Mac: open question (PRD Q16). Xcode 16 or later is assumed | |

**Open question (depends on the Duo SDK):** if the app ships Duo-only, the true floor is whatever iOS the Duo runs, and raising the deployment target costs nothing. If the Duo posture API exists only in a newer SDK, it is called behind `#available` from the adapter in §5 so the minimum can stay at 18.0 for other iPhones. Both the Duo's OS version and the API names are **unverified** here.

**Unverified:** that `TextRenderer` exposes everything in §8. This is the first thing to prove on a Mac (M1 acceptance). The fallback is described in §8.

## 3. Build reproducibility: XcodeGen (recommended) versus SwiftPM-only

| | XcodeGen `project.yml` | SwiftPM-only app | Hand-written `.xcodeproj` (earlier scaffold) |
|---|---|---|---|
| What is committed | A short YAML file | `Package.swift` | A large generated-looking `project.pbxproj` |
| Reviewable in a diff, writable on Linux without Xcode | Yes | Yes | No — easy to corrupt, impossible to verify here |
| iOS app features (Info.plist keys, `UIAppFonts`, StoreKit configuration in the scheme, entitlements, asset catalogs, privacy manifest, launch arguments) | All supported | Not properly supported for a shippable iOS app | Supported |
| Extra tool on the Mac | `brew install xcodegen` | None | None |

**Decision: XcodeGen.** `project.yml` is the source of truth; `Omramo.xcodeproj` is generated by `xcodegen generate` and is **git-ignored**. `OmramoCore` stays a normal Swift package referenced by path, so it is also buildable and testable alone with `swift build` / `swift test`.

Rules that keep the build reproducible:

- No third-party Swift packages. Nothing to resolve, nothing to audit for the Kids Category.
- Bundle identifier, display name and version live in `Configuration/*.xcconfig`. Signing team is in an untracked `Configuration/Signing.local.xcconfig` (never committed).
- `docs/BUILD.md` (an M1 deliverable) gives the exact commands: install XcodeGen, generate, run tests, run the app, run in simulated-Duo mode.
- Record the XcodeGen version used in `docs/BUILD.md`.

## 5. Duo two-pane, hinge and folded handling

### 5.1 What is known and unknown

The Duo developer API is **an unknown** to this project. The designs assume two 432 × 720 pt panes and a 28 pt hinge gap; the design notes call this "my assumption, not an Apple spec". The earlier scaffold's comments name `ArrangementView`, `.arrangementViewStyle(.split)` and `GeometryProxy.reservedRegions(kind: .division)` in an "iOS 27.1 SDK", and say Apple's guidance is "compact width for the outer display, regular width for the inner display". I could not verify any of that. **Open question (PRD Q4).**

So the app is built against its own abstraction. Only one small adapter will ever touch the real SDK.

### 5.2 The abstraction (in `OmramoCore/Layout`)

```swift
/// How the device is being held, as far as layout cares.
public enum DisplayPosture: Equatable, Sendable {
    case folded      // one pane: the Duo outer screen, or any ordinary iPhone
    case unfolded    // two panes either side of a hinge (or a virtual gutter)
}

public struct LayoutRect: Equatable, Sendable { public var x, y, width, height: Double }

/// Everything a screen needs to lay itself out. Screens never ask what device they are on.
public struct PaneLayout: Equatable, Sendable {
    public var posture: DisplayPosture
    public var canvas: LayoutRect      // the whole window, in points
    public var leading: LayoutRect     // the only pane when folded
    public var trailing: LayoutRect?   // nil when folded
    public var hinge: LayoutRect?      // region with no pixels or no touch; nil when folded
    public var source: Source          // .system (real SDK), .derived (from size), .simulated (debug)

    /// Scale from the 432 × 720 reference pane to the real pane, for positions in DESIGN.md.
    public var referenceScale: Double { get }
}

/// Raw facts gathered by the app layer.
public struct PaneLayoutInput: Equatable, Sendable {
    public var canvasWidth: Double
    public var canvasHeight: Double
    public var reportedHinge: LayoutRect?        // from the Duo SDK when available, else nil
    public var reportedPosture: DisplayPosture?  // from the Duo SDK when available, else nil
    public var simulation: Simulation?           // debug override
}

public struct PaneLayoutResolver: Sendable {
    public var minimumPaneWidth: Double = 360    // assumption
    public var virtualGutter: Double = 28        // matches the design's hinge gap
    public func resolve(_ input: PaneLayoutInput) -> PaneLayout
}
```

Resolution order — a pure function, fully unit-tested:

1. **Simulation set** (debug only) → build exactly the requested layout (see 5.4).
2. **SDK reported a hinge rectangle** → panes are the canvas areas either side of it; posture unfolded.
3. **SDK reported a posture but no hinge** → unfolded splits the canvas in half around a zero-width hinge; folded is one pane.
4. **No SDK information** → derive from size: if `canvasWidth ≥ 2 × minimumPaneWidth + virtualGutter` **and** `canvasWidth > canvasHeight`, treat as unfolded with a centred virtual gutter; otherwise folded. An ordinary iPhone in portrait therefore gets the folded layout, and a landscape iPad (if ever supported) gets two panes.

### 5.3 App-side provider

```swift
@MainActor protocol PaneLayoutProvider {
    func input(for size: CGSize) -> PaneLayoutInput
}
```

| Implementation | When | Behaviour |
|---|---|---|
| `DerivedPaneLayoutProvider` | Default on every device today | Supplies size only; rule 4 applies |
| `SimulatedDuoProvider` | Debug builds, launch argument `-OmramoPosture unfolded` or `folded`, or a debug menu toggle | Supplies a `Simulation` |
| `DuoSDKPaneLayoutProvider` | Once the SDK is known (milestone "Duo hookup") | Reads posture and hinge from the system and fills `reportedHinge` / `reportedPosture`. **The only file that references Duo APIs**, compiled behind `#if` / `#available` |

`PaneLayoutReader` is a SwiftUI view that measures its size with `GeometryReader`, asks the provider and the resolver, and publishes `PaneLayout` through the environment. A change of size or posture produces a new value and SwiftUI re-lays out.

`TwoPane { scene } leading: { … } trailing: { … }` places the scene across the whole canvas (including under the hinge) and the two pane contents in their rectangles. When folded it shows a single-pane composition supplied by the feature. Features provide both compositions; they never test device models or size classes themselves.

### 5.4 Simulated Duo (works on a normal iPhone and in the simulator)

In `unfolded` simulation the app draws the 892 × 720 reference canvas — two panes with a black 28 pt band between them — scaled to fit the available window (letterboxed), in landscape. This reproduces the screenshots in `docs/design/` on any simulator, which is how layouts are checked before hardware exists. In `folded` simulation it draws one 432 × 720 pane scaled to fit. The simulation is compiled out of Release builds.

### 5.5 Rules every screen follows

- **Gutter:** no text and no touch target inside `hinge`, and none within 20 pt of it (the designs keep 28–30 pt).
- **Scene continuity:** scene art is authored for the whole canvas; the strip under the hinge exists in the image but is not visible on hardware. Nothing essential is drawn there.
- **Card placement** (`CardPlacement`): a tap-to-see or character card opens on the pane opposite the tapped word. With text on both panes it covers the far pane. Folded: a bottom card (assumption A2).
- **Continuity across fold/unfold:** state lives in feature models keyed by content anchors (§8.4), not in views, so a posture change re-lays out the same page, keeps an open card open, and never resets position.
- **System chrome:** the status bar, Dynamic Island and home indicators belong to iOS. Views use safe-area insets per pane. How safe areas are reported per pane on the Duo is **unverified**.

### 5.6 Open questions (Duo)

1. Real pane sizes, hinge width, and whether the hinge region has pixels.
2. The posture and hinge API names, their SDK version, and whether half-open postures exist.
3. Whether one window spans both panes by default or the app must opt in; whether a second scene is needed.
4. Orientation: is the unfolded device used only with the hinge vertical?
5. Whether the earlier scaffold's size-class rule ("regular width = inner display") holds on the device.

## 6. Story content format

### 6.1 Principles

- **Versioned.** `schemaVersion` is an integer. The app refuses a file whose version is newer than it supports, with a friendly error, and may migrate older ones.
- **A page is an authored spread.** The unit the page indicator counts, the unit that owns one scene, the unit "pages read" counts, the unit of the free sample. It is the same folded and unfolded.
- **Stable IDs** for stories, spreads, blocks, tap targets and characters. Progress and "seen" state refer to IDs, so a corrected story does not lose a child's place.
- **Text as runs.** Each paragraph is an ordered list of runs. Concatenating the run texts gives the paragraph exactly; the validator checks that against the source text so wording is never changed by markup.
- **Art by reference.** JSON names image files relative to the story folder. No image data in JSON.
- **One tier per story**, stored on the story.

| **Story** | `schemaVersion`, `id`, `contentVersion`, `title`, `subtitle?`, `tier` (`low` \| `medium` \| `advanced`), `language` (`en`), `origin`, `source`, `review`, `sample`, `theme`, `cover`, `parts[]`, `characters[]`, `tapTargets[]`, `spreads[]` |

### 6.5 Catalog

`catalog.json`: `{ "schemaVersion": 1, "catalogVersion": 1, "stories": ["monkey-and-crocodile", …] }`. The library reads each story's header fields (title, tier, origin, cover, spread count). If loading whole story files for the library becomes slow with a larger catalog, a generated `index.json` with just the headers is added; not needed for three stories.

### 6.6 Open questions (content)

1. Who supplies page breaks, tap words and card copy (PRD Q18)?
2. Runs versus stand-off ranges: runs are chosen because they are easy to hand-author and validate for three stories. A future authoring tool may prefer ranges; the model can load either behind `StoryDecoder`.
3. Does a story need per-spread text colour (a scene that changes from light to dark mid-story)? The schema allows a `chrome` override per spread; a `textColor` override can be added the same way.

## 7. Tap-to-see asset pipeline: authoring → validation → bundling

### 7.1 Authoring (outside the app)

1. Editor fixes the story text and marks: page breaks, lead sentences, voices, names, sound words, and the tap-to-see words (design rule: few per page; a hard cap is an open question).
2. For each tap target, the editor writes the title, the one line to read, the culture note and the alt text; a cultural reviewer signs off (`review.culture`).
3. Illustrator delivers masters per the size table below. Layered source files stay in the art team's storage, not in this repo.
4. JSON is hand-written for the three prototype stories. An internal authoring tool is a later project (not in this plan).

### 7.2 Image formats and sizes (@3x of the 432 × 720 pt reference pane)

| Asset | Pixel size | Format | Notes |
|---|---|---|---|
| Scene, unfolded | 2676 × 2160 | HEIC (lossy, high quality), sRGB | Spans both panes and the 84 px hinge strip. Keep faces and essentials out of the strip and out of the text area |
| Scene, folded | 1296 × 2160 | HEIC | Picture in the top ~47% (to about 1020 px), calm pale area below for text. May be a recomposition, not a crop |
| Tap-to-see picture | 1296 × 1212 (432 × 404 pt) | HEIC | Bottom ~320 px fades into the card background colour |
| Character portrait | 1296 × 1200 (432 × 400 pt) | HEIC | |
| Face chip / avatar | 144 × 144 | PNG with alpha | Shown from about 18 pt (inline chip) to 48 pt (avatar) |
| Cover | 720 × 900 (4:5; shown up to 372 × 186 pt cropped, and 116 × 134 pt) | HEIC | No title baked in |

Assumptions: one @3x master per image, downscaled by the system; HEIC for opaque art, PNG where alpha is needed. Actual file sizes and the app-size budget can only be set from real art — **open question**. Images are loose files, not asset-catalog entries, so the same loader serves bundled and downloaded stories. "Lightly animated" visuals, if ever wanted, are layered stills moved in code, never video.

### 7.3 Validation

Two checkers with the same rules:

- **`StoryValidator` in `OmramoCore`** — the authority. Used by unit tests (every bundled story must validate) and at load time in debug builds.
- **`tools/validate_content.py`** — Python 3, standard library only. Exists because the development box has no Swift toolchain; lets content be checked on Linux and in any CI. If the two ever disagree, the Swift one wins and the script is fixed.

Checks: schema shape and version; unique IDs; all references resolve; every image exists with the declared pixel size and required dimensions for its role; alt text present; no run with both `tap` and `name`; text fidelity (concatenated runs equal the source text after normalising typographic quotes, dashes and whitespace — sources live in `Content/sources/`); warnings for tap targets per spread above a threshold, words per spread outside the tier's range, and `review` fields still `pending` (an error for a release build).

### 7.4 Bundling

`Content/` is added to the app target as a folder reference in `project.yml`, so the directory structure is preserved in the bundle. `DirectoryContentRepository(root: Bundle.main…/Content)` reads it. Package tests read the same folder from the repo by a path relative to the test file, so there is one copy of the content.

Image loading: decode off the main thread, downsample to the displayed pixel size, keep the current and next spread's scenes in a small cache, release on memory warning.

## 8. Reader architecture

### 8.1 Screen composition

```
ReaderScreen (PaneLayout from environment)
 ├─ SceneLayer        one image across the canvas (unfolded) or the pane (folded)
 ├─ TextLayer         StoryTextView per pane (or one, folded)
 ├─ ChromeLayer       back, crumb, Aa + bookmark, chips, page chip, page-turn button
 ├─ HoldLayer         beam + place marker when a card is open or just closed
 └─ CardLayer         TapToSeeCard / CharacterCard on the facing pane, or bottom card folded
ReaderModel (@Observable)   position, open card, seen targets, sample gate, text scale
```

### 8.2 Text rendering

Requirements from `docs/DESIGN.md` §4.3: per-run font, weight and colour; inline face chips; rounded highlight behind tap words with an underline and a spark; dotted underlines; a larger display-face sound word inline; hit-testing of individual words; the rectangle of the tapped paragraph for the marker and beam; text on a curve.

**Plan (to be proven on a Mac in M1):**

- Build one `Text` per paragraph by concatenating styled `Text` segments from the runs. Face chips are inline images. Tap and name runs carry a custom `TextAttribute` holding the target ID.
- A `TextRenderer` (`StoryTextRenderer`) draws the highlight shapes, underline and spark behind or over the runs that carry the attribute, and reports each marked run's rectangles upward through a preference.
- An overlay places an invisible, accessible `Button` over each reported rectangle, enlarged to at least 44 × 44 pt. The button is what is tapped and what VoiceOver finds.
- The paragraph's frame, reported by anchor preference, positions the place marker and beam.
- Text on a path (`pathText`) is drawn glyph by glyph in a `Canvas` along the authored curve, with the plain string as its accessibility label.

**Fallback if `TextRenderer` cannot do this** (unverified): mark runs as links in an `AttributedString` with a private URL scheme and intercept `openURL`. That gives tapping and accessibility for free but not custom highlight shapes or rectangles; the highlight would degrade to a background colour and the marker to the paragraph frame. A TextKit-backed `UITextView` wrapper is the heavier third option.

Variable fonts: SwiftUI cannot set `opsz`/`wdth`/fractional `wght` directly. `OmramoFont` builds a `UIFont` from a `UIFontDescriptor` with `kCTFontVariationAttribute` values and wraps it in `Font`. Line height is enforced with line spacing computed from the font's metrics so the 37 / 32 / 27 pt line heights are exact. Word spacing from the design (+0.3 to +0.6 pt) has no direct SwiftUI control; it is approximated or dropped (accepted deviation, to review by eye).

### 8.3 Pagination and overflow

A spread's text is authored to fit its pane at the tier's designed size. If it does not fit — larger text chosen with "Aa", a smaller real pane, the folded screen — the spread continues on **continuation screens**: same page number, same scene, next slice of paragraphs. The page-turn button advances through continuation screens first, then to the next spread. The page indicator and "pages read" count spreads, not screens, so counts are stable across devices and text sizes. `Pager` (core) owns this arithmetic; the view measures what fits and tells the model the split points.

Reading text never scrolls freely (assumption, consistent with "a page turns only when the child presses the round button"); whether folded mode may scroll instead is an open question for the design pass on gaps G4/G8.

### 8.4 Reading position and continuity

`ReadingPosition { storyID, spreadID, blockID? }`. Saved on every page turn and when the app backgrounds. On a posture change the reader re-lays out the same spread and shows the screen containing `blockID`. An open card (`ReaderModel.openCard`) survives the change and moves to the placement the new posture requires.

### 8.5 Sample gate

`SampleGate.access(spreadIndex:, freeSpreads:, entitlement:)` → `.read` | `.endOfSample` | `.wait`. The reader asks it for every spread it is about to show, so a lapsed subscription locks pages in place rather than trusting navigation. At the last free spread the page-turn button is replaced by the end-of-sample card.

## 9. StoreKit 2 subscriptions

### 9.1 Design

- **One subscription group**, family plan. Product identifiers are placeholders until PRD Q7: `com.omramo.family.monthly` and, if a yearly plan is wanted, `com.omramo.family.yearly` (assumption A8). The app lists whatever products of the group StoreKit returns, so adding a plan needs no layout rewrite beyond a second plan card.
- **No server at M1 or for the MVP.** StoreKit 2 verifies transactions on the device. Identity is the Apple Account. No Omramo account, no receipt upload.
- **Prices are never in the app.** The plan card shows `Product.displayPrice` and the subscription period from StoreKit. With no product available it shows the designed "TBD — price not set yet" state in debug, and "Not available right now" with Restore still working in release.

```
EntitlementBackend (protocol, OmramoCore)
 ├─ StoreKitEntitlementBackend     app; Product.products, purchase(), Transaction.currentEntitlements,
 │                                 Transaction.updates, AppStore.sync()
 └─ SimulatedEntitlementBackend    app; in-memory, for UI work and tests (-OmramoSimulatedStore)
EntitlementStore (@Observable, @MainActor)   holds EntitlementState, starts listening at launch
EntitlementGate / SampleGate (pure, core)    every screen asks these; none decides alone
```

### 9.2 Behaviour

| Topic | Behaviour |
|---|---|
| **States** | `unknown` (store not yet answered → screens wait, the paywall never flashes), `notSubscribed`, `subscribed(productID, expires, viaFamilySharing)` |
| **Purchase** | Only reachable after the grown-up gate. `Product.purchase()`; `.success` verified → finish → entitlement refreshed; `.pending` (Ask to Buy) → a "waiting for approval" message, resolved later through `Transaction.updates`; `.userCancelled` → nothing |
| **Family Sharing** | Enabled per product in App Store Connect by the owner (future owner action). Family members' entitlements arrive in `Transaction.currentEntitlements` like any other; `ownershipType == .familyShared` is recorded only to word the Manage Subscription row correctly. No extra code path gates reading |
| **Restore** | "Restore Purchases" (subscription screen and settings, both behind the gate) calls `AppStore.sync()`, then re-reads entitlements |
| **Manage** | "Manage Subscription" opens the system manage-subscriptions sheet |
| **Revocation, expiry, refund** | `Transaction.updates` and a re-check on every foreground; revoked or expired → `notSubscribed`; the reader's per-spread gate locks pages beyond the sample |
| **Entitlement cache (offline)** | The last verified state is saved to a small file: product ID, expiry date, ownership type, time verified. At launch the cache is applied immediately so a subscribed child can read offline (plane, no signal), then replaced by the live answer when StoreKit responds. A cached subscription is honoured until its recorded expiry plus a grace window; the grace length is **TBD — open question** (Example (not a decision): 7 days) |
| **Sample gating** | First `sample.freeSpreads` spreads of every story are readable in any state, including `unknown` |
| **Local testing** | `Configuration/Omramo.storekit` attached to the scheme gives real StoreKit 2 flows in the simulator with **Example (not a decision)** prices. Those example prices are test fixtures only and must never be read as pricing |

### 9.3 Unknown / unverified

- Whether Family Sharing can be switched off again after being enabled for a product, and family-group limits.
- Current App Review expectations for the wording beside the Subscribe button (the designed terms paragraph is a sensible default).
- Whether any Kids Category rule constrains free trials or introductory offers.
- Final product identifiers, plan structure, trial (PRD Q7); the bundle identifier (PRD Q20).
- If a server is ever needed (cross-platform access, school licences), App Store Server Notifications is the route. Not in scope.

## 10. Privacy, COPPA and App Store Kids Category

### 10.1 Position

**Collect nothing.** No account, no child profile data leaving the device, no analytics, no advertising, no third-party SDK, no network calls by app code at all in the MVP. The only network activity is the operating system's own StoreKit traffic and, behind the grown-up gate, opening the legal pages.

### 10.2 Constraints and how the build meets them

The rule statements in the left column are taken from the 13 Nov assessment, which quoted Apple's and the FTC's pages; they were not re-fetched in this run.

| Constraint | Implementation |
|---|---|
| Kids Category: no links out, purchasing opportunities or other distractions unless behind a parental gate | One `GrownUpGate` component in front of: the Grown-ups tab, the subscription screen, Restore, Manage Subscription, Privacy, Terms, and any `openURL`. A single `ExternalLink.open(_:)` helper is the only code allowed to open URLs and always goes through the gate. A unit/UI test fails if a purchase call is reachable without a passed gate |
| The child is never shown a price or a buy button | End-of-sample card says only "Ask a grown-up to unlock" |
| No third-party analytics or advertising | Zero dependencies. A check in `docs/BUILD.md`'s release checklist: `project.yml` and `Package.swift` list no remote packages |
| Do not transmit personal or device information to third parties | No network code. No identifiers generated. No `IDFA`, no `identifierForVendor` use |
| A parental gate is not parental consent | Because nothing is collected, verifiable parental consent should not arise. **This is a design position, not legal clearance** — a children's-privacy review is an owner action (PRD Q20) |
| Age band must be chosen (5 and under / 6–8 / 9–11) | Open question (PRD Q2) |
| COPPA (US), GDPR-K (EU), UK children's code | Collect-nothing is the right default for all three; legal review before a global launch is an owner action |
| No notifications aimed at the child | No notification permission is requested in the MVP |
| Gate must be an adult-level task | `GateChallenge`: random digits shown as words, typed on a keypad (design concept; PRD Q9). New digits on each presentation and after each wrong answer |

### 10.3 Data stored on the device

| Data | Where | Leaves the device? |
|---|---|---|
| Reading position per story | App support directory (JSON file) | No |
| Reading log: page-read events as (local date, story ID, spread ID) — **no times of day, no durations** | App support directory | No |
| Seen tap targets, friends met, finished stories | App support directory | No |
| Appearance and text-size settings | `UserDefaults` | No |
| Entitlement cache | App support directory | No |

Files are excluded from nothing special; they ride in the user's normal device backup. Optional iCloud sync is out of scope.

### 10.4 Privacy nutrition label and manifest

- **App Store privacy label (owner action later):** expected answer "Data Not Collected". To be confirmed against Apple's definitions at submission time — unverified here.
- **`PrivacyInfo.xcprivacy`:** tracking false; no tracking domains; no collected data types; required-reason API declarations for the APIs the app actually uses (expected: `UserDefaults`, and file timestamp APIs if used). Exact reason codes to be confirmed in Xcode — unverified here.
- **In-app Privacy row:** "No ads · No tracking", leading (behind the gate) to a short plain-language statement and the policy link.

### 10.5 Analytics: none remote, minimal on-device

There is no remote analytics. The on-device reading log above exists for the product itself (parent view, streak, shelf). The metrics in `docs/PRD.md` §9 are computed from that log in moderated tests. A parent-initiated "export reading log" for pilot families is a P2 idea and would sit behind the gate.

A stricter event log for tests (tap-to-see opened/closed, page dwell for the fast-flip metric) is compiled only into a **test build configuration**, never into the release build, so the shipped app holds no timing data at all. Whether the pilot needs it: open question (PRD Q12, Q14).

## 11. Offline content: bundled now, packs later

| Stage | Mechanism |
|---|---|
| **M1 → MVP** | All stories inside the app bundle under `Content/`. Works offline from first launch. No network code |
| **Later (P2)** | A remote catalog plus one downloadable pack per story: a folder identical to a bundled story folder, zipped, with a manifest carrying `schemaVersion`, `contentVersion`, byte size and a SHA-256 digest. Packs unpack into Application Support; `ContentRepository` merges bundled and downloaded stories by ID, highest `contentVersion` wins |

Design decisions already made so packs are cheap later: stories are self-contained folders; images are loose files; all references are relative; the repository reads from any root directory; IDs are stable.

Open for the packs stage (not needed now): hosting. Apple-hosted assets (Background Assets) would keep Omramo out of the data path; a self-hosted CDN would see device IP addresses and so changes the privacy disclosures. Both are unverified here and need a decision when the stage is planned.

## 12. Accessibility

### 12.1 Text size with fixed tier sizes

The tier sizes (23.5 / 19.5 / 16.5 pt) are the design at the default size. Strategy:

1. **Tier base × reader scale.** Effective size = tier size × `textScale`. Line height, paragraph gap and lead-sentence size scale by the same factor, so the proportions in `docs/DESIGN.md` §4.2 are preserved.
2. **"Aa" control** sets `textScale` in steps. Proposed steps (estimate; the panel is design gap G1): 0.9, 1.0, 1.15, 1.3, 1.5.
3. **System Dynamic Type sets the starting step** the first time: default and smaller sizes → 1.0; larger system sizes map to higher steps; accessibility sizes start at 1.5. After that the child's or parent's own choice is kept.
4. **Overflow never truncates**: text that no longer fits continues on a continuation screen of the same page (§8.3).
5. **UI chrome** (chips, labels, buttons, parent view, subscription screen) uses fixed design sizes wrapped in scaled metrics with a cap, so the composed two-pane layouts do not break; the parent view and subscription screen become scrollable at large sizes.

Tier order is preserved at every step (Low is always larger than Medium, Medium larger than Advanced).

### 12.2 VoiceOver and other assistive technology

- System accessibility is never disabled or blocked. VoiceOver reading story text aloud is allowed; that is the system's feature, not an Omramo read-aloud control.
- Reading order: crumb → paragraphs in order (leading pane, then trailing) → page indicator → page-turn button. Scene art is one image element with its alt text, after the text.
- Each paragraph is one accessibility element whose label is the plain paragraph text. Tap words and names are exposed as custom actions on the paragraph ("Show picture: Rin Gin", "About: the Monkey") and as the overlay buttons.
- Face chips are decorative (hidden); the voice is conveyed by the text itself ("said the Crocodile").
- Cards: focus moves to the card title when it opens; the card is a modal region; "Back to my line" returns focus to the paragraph that was tapped. The toast is announced.
- Page-turn button label "Next page"; value "Page 5 of 14". Tier chip label "Level: Low". Origin chip label "From ancient India".
- Parent chart has a text summary ("25 pages in the last 7 days; read on 6 of 7 days") and per-day values.
- Gate: digit words are read by VoiceOver; keypad keys are standard buttons.
- Switch Control and full keyboard access follow from using real buttons.

### 12.3 Reduce Motion, contrast, colour

- Reduce Motion: page changes and card presentation become cross-fades; no drift, scale or parallax (`docs/DESIGN.md` §3.7).
- Increase Contrast: glass fills become near-opaque; dimmed paragraphs go to 60% instead of 42%; highlight underline thickens.
- Reduce Transparency: glass becomes a solid tint.
- Differentiate Without Colour: already met — marked words carry underline and spark.
- Contrast of body text over art is a content rule checked in art review; a debug overlay can sample contrast under the text column (P2).

### 12.4 Open questions (accessibility)

- "Aa" steps and whether the panel also offers line spacing or a higher-contrast text plate behind the text (G1).
- Dark appearance (G7): the reading scenes carry their own light, so Appearance affects only the library, parent view and sheets. Confirm.

## 13. Persistence

Small JSON files in Application Support, each owned by one store type with a protocol in the core (`ReadingProgressStore`, `ReadingLogStore`, `EntitlementCacheStore`) and a file-backed implementation in the app. In-memory implementations serve tests and previews. No database; the data is tiny. Writes are atomic. A `schemaVersion` field in each file allows migration.

Day boundaries for the streak and the 7-day chart use the device's current calendar and time zone; only the date is stored.

## 17. Assumptions (architecture)

2. `TextRenderer` can supply run rectangles for highlights and hit areas; a link-based fallback exists if not.
